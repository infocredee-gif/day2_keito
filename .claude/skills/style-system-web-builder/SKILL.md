# style-system-web-builder

デザインシステム（自分のブランドの決まりごと）と、デザイン見本集（世界観のバリエーション）を
掛け合わせて、1本のWebサイトを作るための手順書。

なぜ2つを組み合わせるのか：
デザインシステムだけだと毎回同じ見た目になり、見本集だけだとブランドから外れる。
**「ブランドとして絶対に崩さない部分」は design-system が決め、「今回の空気感」は style-vault が決める。**
この役割分担を最初に決めておくと、後戻りがなくなる。

作業の成果物は、いま作業しているプロジェクトの直下に置く。

```
./design-application.md   ← 今回の適用方針（実装前に必ず作る）
./site/                   ← 完成したWebサイト
./site/images/            ← 生成した画像（相対パスで参照）
```

このスキルには特定のブランド名も、特定のPCの絶対パスも書かない。
素材は毎回「探して見つける」。そうしないと別のブランド・別の環境で使えなくなる。

---

## 手順

### 1. 素材を確認する

`design-system/` と `style-vault/` を探す。どちらも `skills/` フォルダの中にあるのが基本形。
見つからないときは、下の候補を上から順に探す（相対パスで探索し、絶対パスは決め打ちしない）。

```
./skills/design-system/            ./skills/style-vault/
./.claude/skills/design-system/    ./.claude/skills/style-vault/
./.agents/skills/design-system/    ./.agents/skills/style-vault/
~/.claude/skills/design-system/    ~/.claude/skills/style-vault/
```

見つけたら、まず中身の地図だけ作る（この時点では全文を読まない。全部読むとトークンを使い切る）。

- `design-system/` … README / SKILL.md の見出し、`tokens/` や CSS ファイル名、`components/` の一覧、`assets/` に何の画像があるか
- `style-vault/` … スタイルが何件あるか、1件あたり何のファイルがあるか（`DESIGN.md` / `index.html` / slug）

**どちらも見つからない場合は、ここで止めてユーザーに置き場所を聞く。**
推測でそれらしいデザインを作り始めない。ブランドの決まりごとを外した時点で、作り直しになる。

### 2. 足りない情報だけ聞く

決めるべきは5つ。

| 項目 | 何を知りたいか |
|---|---|
| 用途 | 何のためのサイトか（商品LP／会社紹介／採用／キャンペーン など） |
| 読者 | 誰が見るか（見込み客・既存客・取引先・応募者。年齢層や知識レベルも） |
| 見てほしい行動 | 見た人に何をしてほしいか（購入・問い合わせ・LINE登録・資料請求） |
| 好み | 好きな雰囲気、避けたい雰囲気、参考にしたいサイト |
| ブランドルール | 絶対に守ること（ロゴの扱い、使ってよい色、書いてはいけない表現、薬機法などの表現制限） |

**会話の中ですでに分かっていることは聞き直さない。** 聞き直されると「話を聞いていない」と感じる。
不足している項目だけを、**一度に1〜3問**にまとめて聞く。1問ずつ往復すると疲れるし、
5問以上を一度に投げると答えるのが面倒になって精度が落ちる。

### 3. 選択式で聞く

質問は自由記述ではなく、**選択肢を出して選んでもらう形**にする。
デザインの好みは言語化が難しいので、選択肢があるほうが答えやすく、答えも正確になる。

- Claude Code … `AskUserQuestion` ツールを使う
- Codex … その環境で使える質問ツール（選択式のもの）を使う
- どちらも使えない … 普通の会話で「A / B / C」の形で提示し、**返事を待つ**

選択肢には必ず「どういう印象になるか」の一言を添える。専門用語だけの選択肢は選べない。
勝手に決めて先に進まない。ここで外すと、作ったあと全部やり直しになる。

### 4. 見本集から3案を出す

`style-vault/` のカタログを、ステップ2で聞いた用途・読者・行動で検索する。
検索語は「業種名」だけでなく、**狙う印象**（清潔・高級・親しみ・力強い など）でも引く。

目的に合う**3案**を、この形で提示する。

```
案1 ◯◯（slug: xxxx-xxxx）
  違い  ：ひと言で言うとどう違うか（例：写真を大きく使い、余白で静けさを出す）
  向く理由：今回の用途・読者にどう効くか
  見本   ：style-vault/xxxx-xxxx/index.html（DESIGN.md は同じフォルダ）
```

ルール：

- **実在する案だけを出す。** 該当が2件しかなければ2件でよい。3件に揃えるために存在しないslugを書かない（後で開けず、信用を失う）
- 3案は**できるだけ方向性を散らす**。似た3案からは選べない
- 「お任せ」と言われたら、こちらで選ぶ。ただし**採用理由を必ず添える**（何を根拠に決めたかが分かれば、違ったときに直せる）

### 5. 選ばれた案を読み込む

ここで初めて全文を読む。

1. 選ばれたスタイルの `DESIGN.md` を**全文**（要約で済ませない。細部の指定がデザインの質を決める）
2. `design-system/` のガイド、CSS（トークン／変数）、部品の見本

読みながら、両者が**ぶつかっている箇所**をメモしておく。次のステップで使う。

### 6. 優先順位で調整する

競合したら、必ずこの順で決める。

1. **今回の明示指示**（ユーザーが今回はっきり言ったこと）
2. **design-system の固定基準**（ロゴ、ブランドカラー、禁止表現など崩せないもの）
3. **選んだ DESIGN.md**（今回の世界観）
4. **AIの提案**（1〜3で決まらない部分を埋める）

上が下を上書きする。ユーザーの指示より自分の好みを優先しない。
**この順番でも決まらない競合だけ**を質問する。全部聞くと会議になってしまう。

例：design-system のボタンは角丸なし、DESIGN.md は角丸16px → 2が3に勝つので角丸なし。
ただし「今回はやわらかく見せたい」と言われていれば1が勝つので角丸を採用。

### 7. 方針を design-application.md に保存する

実装前に、決めたことを1枚にまとめる。頭の中だけに置くと、作っている途中でブレる。
ファイルに書いておけば、後から「なぜこの色なのか」を追える。

```markdown
# 今回のデザイン適用方針

採用スタイル：◯◯（slug: xxxx-xxxx）

## 守る点（design-system の固定基準）
- …

## 取り入れる点（選んだ DESIGN.md から）
- …

## 今回は使わない点（理由つき）
- …

## 採用する値
| 項目 | 採用値 |
|---|---|
| 色   | 主 #xxxxxx ／ 文字 #xxxxxx ／ 行動を促す色 #xxxxxx ／ 背景 #xxxxxx |
| 文字 | 見出し（書体・サイズ）／本文（書体・サイズ）／行間 |
| 余白 | 基準の刻み（例 8px）／セクション上下 |
| 形   | 角丸 ／ 枠線 ／ 影 |
| 写真 | 雰囲気・色味・撮り方・加工の有無 |
| 動き | 何をどのくらいの速さで動かすか（動かさないならそう書く） |
```

**採用する値は、項目ごとに1つに絞る。**「#0055aa または #1166bb」のように候補を残すと、
実装のたびにブレて、ページごとに違う見た目になる。

### 8. 画像を生成する

`design-application.md` の「写真」欄をそのまま画像生成の指示に落とす。ここで方針から外れると、
せっかく揃えた世界観が画像だけ浮く。

**Codex の場合** … その環境の画像生成ツールをそのまま使う。

**Claude Code の場合** … 画像生成にOpenAIのAPIキーが必要。

```bash
[ -n "$OPENAI_API_KEY" ] && echo "設定済み" || echo "未設定"
```

- **未設定** … 生成に進む前にユーザーへ伝える。
  「画像生成には環境変数 `OPENAI_API_KEY` の設定が必要です。設定いただければ生成します。
  先に進む場合は、画像を入れる場所を四角の枠（プレースホルダ）にしてサイトを作ります」
  と伝え、**どちらにするか返事を待つ**。
- **設定済み** … `scripts/generate_image.py` を使って `site/images/` に生成する。

```bash
python3 <スキルのパス>/scripts/generate_image.py \
  --prompt "画像の指示" --out site/images/hero.png --size 1536x1024
```

画像の指示を書くときのコツ：

- `design-application.md` の色味・雰囲気の言葉をそのまま入れる（例：清潔、高明度、青みのある白）
- **文字・ロゴ・数字は画像の中に入れない。** AI画像の文字はほぼ崩れる。文字はHTML側で乗せる
- 人物の顔をはっきり出す画像は、肖像の扱いで揉めやすい。後ろ姿・手元・引きの構図を優先する
- 健康・美容の商材では、**効果が出たように見える演出（ビフォーアフター、施術結果）を作らない**。
  薬機法・景品表示法に触れる。使うのは原料・製造・使用シーンなど事実に基づく画像にする
- 横長（ヒーロー）と正方形（カード）で必要なサイズが違う。用途ごとにサイズを指定する

### 9. サイトを作る

ユーザーから渡された掲載内容（文章・商品情報・会社情報）をもとに `site/` へ実装する。

- **掲載内容を勝手に作らない。** 実績・数値・お客様の声を創作すると、そのまま公開されて事故になる。
  足りない箇所は `【要確認：〇〇】` と書いて残し、最後に一覧で報告する
- `design-system/` に部品（コンポーネント）があれば、それを使う。ゼロから書き直さない
- 画像は**相対パス**で書く（`images/hero.png`）。絶対パスにすると、サーバーに上げた瞬間に表示されなくなる
- 色・サイズ・余白はCSS変数にまとめ、`design-application.md` の「採用する値」と一致させる
- 画像には `alt`（画像の説明文）を入れる。読み上げ環境と検索の両方で効く
- 1ページで収まらない場合も、まず主要ページを完成させてから増やす

### 10. PC幅とスマホ幅で確認する

作ったら必ず両方の幅で表示して、目で見て直す。SNS集客なら**閲覧の大半はスマホ**なので、
スマホ幅が崩れているのは致命的。

- PC幅：1280px前後　／　スマホ幅：390px前後

確認する項目：

| 見るところ | 直すべき状態 |
|---|---|
| 文字 | 小さすぎて読めない、行間が詰まりすぎ、見出しが不自然に折れる |
| 画像 | つぶれる・伸びる、スマホで見切れる、読み込まれていない |
| ボタン | 指で押せない大きさ（目安44px以上）、文字がはみ出す |
| リンク | 押しても飛ばない、リンク先が空 |
| 横へのはみ出し | 横スクロールが出る（`document.documentElement.scrollWidth > window.innerWidth` で検出できる） |

Playwright などで実際に表示・スクリーンショットが撮れる環境ならそれを使う。
**実際に確認できなかった項目は「未確認」と正直に書く。** 見ていないものを「確認済み」と書くと、
ユーザーは確認せずに公開してしまう。

### 11. 報告する

最後に、この5点をまとめて伝える。

1. **選んだスタイル** … 名前とslug、選んだ理由
2. **適用した基準** … 守った点・取り入れた点・使わなかった点（`design-application.md` へのリンク）
3. **生成した画像** … 何を何枚、どういう指示で作ったか
4. **保存先** … `site/` の構成、確認方法（ブラウザで `site/index.html` を開く）
5. **確認結果** … PC幅・スマホ幅で見た結果、直した点、**未確認の項目**、`【要確認】`として残した箇所

専門用語を使うときは、ひと言添える（例：「トークン（色やサイズを名前で管理する仕組み）」）。
報告は、次に何をすればいいかが分かる形で終える。
